## Why (coordinator's measurement, to be verified by you, not trusted)
On the SEGEVAL-1 draw (150 unseen lines, `docs/records/harvest/collect_v3_admission/segeval1/`), 27 of the 29 false positives come from the two "OCR output too little/too much for the text box" verdicts. For long lines with 1.5–2.3° of skew the upright tight box around the text components is 40–49 px tall while the detected row is 25–35 px tall, so the frozen predictor expects far fewer characters than Google produced (ratios 1.51–1.77). Rotating the text-component pixels by the detected main-row baseline angle and taking the tight box gives ratios 0.82–1.35 on those lines (c82ac45f-p000087-l0021, 00c322b3ee04b419d1979f22-p000028-l0002, 43de3c6e6a7113a4e661bb7d-p000100-l0023, 66112e132fd96ac8e30e5328-p000159-l0079, gazette_modern--9701a3a500ecbd85--s000-l0139) and leaves upright lines unchanged. Baseline evidence as produced by the production census run (census_02, policy 8334dd40…, 150 rows with `evidence` and `frame`): `docs/records/harvest/collect_v3_admission/segeval1/keys/census02_segmentation_evidence.jsonl`.

## The change (exactly this, nothing more)
Code: `greekocr/harvest/line_pipeline_native.py` (`NativeSegmenter.segment`) and `greekocr/harvest/filtering_assets/crop-tools.py` (`features_from_observation` / `tight_box`). The frozen policy `filtering_assets/segmentation-policy.js` (sha 8334dd40…) and the predictor (`font-models.json`, `scripts/harvest/filter_runtime`) stay byte-identical; `boxLengthJudgement`, `paddingJudgement` and their thresholds are not touched.
1. **Skew angle θ** = angle of the detected main row's baseline, from the `text_lines(glyphs)` row with `side == 'main'` that `segment()` already computes (straight-line fit of its `base` curve, degrees, clockwise positive in image coordinates). No main row → θ = 0. Record it.
2. **Row-frame text box**: the same text components as today (`TEXT_ROLES`: letter, fragment, mark, punct), their ink pixels rotated by −θ about the crop centre, tight box → `length` (long side along the row) and `height` (short side). For θ = 0 the result must equal today's `candidate_text_box` exactly (same integers; guard the float path so that identity holds, e.g. θ = 0 uses the existing `tight_box`).
3. **Length rule input**: `long_side = max(length, height)`, `short_side = min(length, height)` of the row-frame box (today: of the upright box). The policy stays unchanged.
4. **Padding (height) rule input**, per the owner: `total_padding_line_heights = (segment_height − upright_box_height) / rowframe_box_height`, where `upright_box_height` is today's axis-aligned text-box height (the rectangle that bounds the whole skewed line's space) and `rowframe_box_height` is the new short side. The policy's unchanged threshold 1.5 then means: the crop may be as tall as the upright box plus 1.5 skewed-line heights. For θ = 0 this equals today's value exactly.
5. **Evidence**: keep `box_evidence.bbox` (upright, for drawing) and add `box_evidence.row_frame = {angle_deg, length, height, corners: [[x,y]×4] in measurement-frame crop coordinates}`; `padding_evidence` gains `upright_box_height` and `row_frame_height`. Nothing else in the evidence changes.
6. **Versions**: segmentation tool version `0.6` ("0.5 + row-frame text box"); update `scripts/harvest/build_filter_versions.py` and the versions file it writes; policy sha unchanged; report the new toolchain digest.
